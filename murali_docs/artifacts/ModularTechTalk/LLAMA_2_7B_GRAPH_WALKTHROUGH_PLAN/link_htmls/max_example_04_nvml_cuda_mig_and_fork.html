NVML, CUDA and MIG

Copied answers · nvmlCountMayDisagreeWithCUDA(nvml)

NVML provides GPU management information; CUDA provides the interface used to run GPU computations. Their device counts can describe different things, particularly when MIG partitions a physical GPU. (docs.nvidia.com)

1. NVML versus CUDA

Here, “CUDA” specifically means the CUDA Driver API used by MAX.

NVMLCUDA Driver API
Full nameNVIDIA Management LibraryDriver interface within NVIDIA’s CUDA platform
Main purposeMonitor and manage GPUs: temperature, utilization, memory, power, MIG configurationDiscover compute devices, manage contexts and memory, load kernels and launch computations

Meaning of this countPhysical GPUs in NVML’s management viewCompute devices CUDA exposes to this process

NVIDIA documents these roles; MAX’s library loading is in NVML.cpp:27 and CUDADriver.cpp:61. (docs.nvidia.com)

NVML also has separate APIs for enumerating MIG instances. The physical-GPU distinction applies to the particular nvmlDeviceGetCount_v2() call here, rather than every NVML API. (docs.nvidia.com)

2. What is MIG?

MIG = Multi-Instance GPU. On supported NVIDIA GPUs, it partitions one physical GPU into smaller instances with assigned compute and memory resources. Multiple workloads can use these partitions independently. (developer.nvidia.com)

There are two levels:

  • GPU Instance — GI: a partition containing assigned memory resources and compute resources.
  • Compute Instance — CI: a subdivision of a GI’s compute resources. Multiple CIs within one GI share that GI’s memory resources. (docs.nvidia.com)

Example: one physical GPU, partitioned into two GIs, each containing one CI:

One physical NVIDIA GPU
├─ GPU Instance 0
│  └─ Compute Instance 0 → CUDA device ordinal 0
└─ GPU Instance 1
   └─ Compute Instance 1 → CUDA device ordinal 1

NVML physical-GPU count: 1
CUDA compute-device count: 2

This example assumes both instances are exposed to the process and supported enumeration behavior. Starting with driver R570, CUDA can enumerate across multiple GIs, with one CI per GI. The number of created partitions is therefore not automatically the number CUDA reports. (docs.nvidia.com)

3. “MIG off” versus “MIG possible” in MAX

“MIG possible” is MAX’s conservative decision label. It includes MIG being enabled or MAX being unable to establish that it is disabled.

The helper checks every physical GPU:

NVML result for a GPUMAX interpretation
Query succeeds; currentMode is disabledMIG is off on this GPU; continue checking
NOT_SUPPORTEDThis GPU does not support MIG; continue checking
Query succeeds; current mode is enabledCounts may differ; use CUDA
Mode query fails, including permission errorsState is uncertain; use CUDA
Obtaining the GPU handle failsState is uncertain; use CUDA

Only when every GPU passes the off/unsupported checks does the helper return false. See nvmlCountMayDisagreeWithCUDA():529.

nvmlCountMayDisagreeWithCUDA(nvml)
├─ false → MIG ruled out across all queried GPUs
│          use NVML's physical-GPU count
└─ true  → MIG enabled or its state uncertain
           initialize CUDA → cuDeviceGetCount()

This is the exact selection at CUDADeviceContext.cpp:566. true does not prove the two counts differ; it means MAX cannot safely assume they match.

The function receives both currentMode and pendingMode, but this decision checks current mode only. Also, failure of the initial NVML count query propagates an error; it does not take the same “MIG possible” branch.

4. Why doesn’t MAX always ask CUDA?

The source explains that CUDA counting requires cuInit(). MAX avoids initializing CUDA merely to count devices when NVML can supply the answer, preserving the ability of subsequently forked children to initialize CUDA themselves. When MIG may affect enumeration, MAX uses CUDA because those device ordinals will later be passed to cuDeviceGet(). See CUDADeviceContext.cpp:549. CUDA documents that ordinal/count relationship. Expanding point 4: MAX defers CUDA initialization when the caller only wants a device count. It still uses CUDA when creating a real GPU device and running computations.

4.1 Why can “just counting GPUs” have consequences?

The CUDA-count path in MAX is:

accelerator_count()
└─ CUDADevice::numberOfGPUs()
   └─ MIG enabled or uncertain
      ├─ CUDADriver::get()
      │  └─ first use: load library, resolve functions, call cuInit(0)
      └─ cuDeviceGetCount(&count)

See counting:574 and initialization:87.

cuInit() initializes the CUDA driver API inside the current process. It can also preload libraries needed for JIT compilation. Thus, answering a discovery question introduces native initialization work and process state. See NVIDIA’s cuInit documentation.

Two distinctions matter:

  • cuDeviceGetCount() does not itself automatically initialize CUDA. MAX initializes its driver wrapper before calling it.
  • Loading libcuda.so.1 is different from initializing CUDA. MAX’s regression test explicitly checks initialization state, because the library can already be mapped through dependencies. See CUDADeviceCountTest.cpp:34.

Counting also does not mean MAX has compiled your graph or allocated its tensor buffers. The real primary-context setup occurs later during device construction: CUDADeviceContext.cpp:904.

4.2 What are “forked children”?

A parent process can call Linux fork() to create another process, called its child.

For example:

Before fork:
PID 1000 · parent Python process

After fork:
PID 1000 · parent continues
PID 1001 · child continues with an inherited memory image

The child has a separate PID and address space. Linux initially shares memory pages using copy-on-write: pages are copied when necessary after modification. Open file descriptors are inherited, and only the thread that called fork() exists in the child. See Linux fork() documentation.

Fork copies the process’s memory image; it does not create a fresh Python interpreter. Python’s multiprocessing exposes this through the explicitly selected "fork" start method. See Python process-start methods.

4.3 Why does initializing CUDA before fork cause trouble?

Consider these two sequences:

A · CUDA initialized before fork

Parent P1
├─ cuInit() → CUDA initialization state exists in P1
└─ fork()
   └─ Child P2 inherits P1's native memory state
      └─ attempt to initialize/use CUDA
         → inherited CUDA state is not supported for this use
B · Parent performs NVML-only discovery

Parent P1
├─ accelerator_count() → NVML route; CUDA remains uninitialized
└─ fork()
   └─ Child P2
      ├─ initializes CUDA for itself
      ├─ creates its own device context/streams
      └─ performs GPU work

The problem is inherited native state, not copying GPU hardware into the child. An initialized library can contain bookkeeping associated with the parent process. Copying its host-memory representation does not reconstruct a valid, independently initialized GPU runtime in the child.

More generally, fork also copies mutex state while other parent threads disappear from the child. This helps explain why native-library initialization and fork interact badly; it is not a claim about NVIDIA’s exact private failure mechanism. See the Linux fork semantics.

For CUDA specifically, MAX’s source records the concrete regression: importing MAX alongside vLLM once initialized CUDA before vLLM forked its CUDA workers, preventing vLLM startup. See CUDADeviceCountTest.cpp:83. This is a source-recorded regression, not a runtime test I performed here.

4.4 What does “children initialize CUDA themselves” achieve?

It lets a parent discover available hardware and organize workers without first initializing their CUDA execution environment.

An illustrative Linux flow, assuming MIG is ruled out and the parent has only performed count-only discovery:

import multiprocessing as mp
from max.driver import accelerator_count

def worker(device_id):
    from max.driver import Accelerator

    device = Accelerator(device_id)
    # CUDA initialization and device setup happen in this child.
    # Construct the session and run GPU work here.

if __name__ == "__main__":
    count = accelerator_count()  # NVML-only route under this assumption

    ctx = mp.get_context("fork")
    child = ctx.Process(target=worker, args=(0,))
    child.start()
    child.join()

The advantage is preserving that process-creation option. Each worker initializes the execution resources it needs within its own process.

This is distinct from current MAX Serve: its model worker explicitly uses "spawn", which starts a fresh interpreter. MAX’s compiler pool uses forkserver. See model_worker.py:797 and compile_pool.py:19.

4.5 Why must MIG counting agree with cuDeviceGet()?

A CUDA device ordinal is the zero-based position of a compute device in this process’s CUDA enumeration.

The calls form a pair:

cuDeviceGetCount(&count);     // How many compute devices?
cuDeviceGet(&device, ordinal); // Give me the device at this position.

Valid ordinals are 0 through count − 1. See NVIDIA’s device API.

Imagine one physical GPU exposing three usable MIG devices to a process:

NVML physical view                 CUDA compute view
──────────────────                 ─────────────────
Physical GPU 0                     ordinal 0 → MIG device A
                                   ordinal 1 → MIG device B
                                   ordinal 2 → MIG device C

Physical count = 1                 Compute-device count = 3

This is an illustration assuming a driver and GI/CI configuration supporting that enumeration; NVIDIA documents the applicable MIG enumeration constraints.

Using the physical count would hide usable compute devices.

MAX’s scan uses:

range(accelerator_count())

If it receives 1, it produces only GPU ID 0. IDs 1 and 2 are omitted, and explicit requests for them can fail count-based validation. See scan_available_devices():111 and load_device():92.

With CUDA’s count 3, the later path remains consistent:

Accelerator(2)
└─ native device/context creation
   └─ CUDADevice::get(2)
      ├─ use descriptor slot devices[2]
      └─ cuDeviceGet(&cuDevice, 2)
         → resolve MIG device C

See CUDADevice::get():845.

Ordinal 2 does not mean physical GPU number 2. After resolving the CUDA device, MAX separately matches its PCI location to the parent physical GPU’s NVML handle. Several MIG devices can therefore resolve to the same physical GPU for management queries. See nvmlDeviceForCudaDevice():246.

When MIG is enabled or uncertain, MAX accepts CUDA initialization during counting to obtain the correct compute-device enumeration. The NVML-only fork benefit applies when that initialization can be avoided.
