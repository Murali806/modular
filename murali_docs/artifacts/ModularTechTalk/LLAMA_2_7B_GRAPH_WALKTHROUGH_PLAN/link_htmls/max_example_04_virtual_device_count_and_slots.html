Virtual device mode · purpose and GPU slots

Copied answer · AsyncRT::getVirtualDeviceCount()

Virtual device mode lets MAX describe and compile for a GPU configuration independently of the GPUs available to that process. Cross-compilation is one use, but the repository also uses it for compilation workers and tests.

1. Why do we need virtual device mode? Is it only for cross-compilation?

Graph construction and compilation need information such as:

Which device receives each operation?  → GPU ID 3
Which programming backend?            → "cuda"
Which target architecture?            → "sm_90"

Virtual mode supplies this information through a VirtualDevice backed by a CompilationDevice. MAX can describe the target without opening a physical GPU. See Device::create.

The repository demonstrates three uses:

UseWhy virtual mode helps
Compile for hardware unavailable locallyA CPU build machine can prepare GPU-targeted code using the configured API and architecture.
Compile for the same hardware using separate workersCompiler workers can use target descriptions instead of each opening the installed GPUs.
Check graph construction and compilation without GPUsTests can inspect graph structure or reproduce compiler failures for configurations requiring several GPUs.

The worker case answers your “only cross-compilation?” question particularly clearly. Its flow is:

Parent process
├─ Load the requested real devices
├─ Read their API and architecture
└─ Pass a target description to compiler workers
   │
   └─ Each worker enables virtual mode
      ├─ Same target API and architecture
      ├─ Same requested GPU IDs
      └─ Compile without opening those physical GPUs

The implementation explains that opening GPUs requires driver initialization, contexts and streams, and can cause contention on a driver lock. Virtual compilation avoids that work in each compiler worker. The target can be the very same GPU installed on the machine. See _CompileTarget.

There are also tests reproducing four-GPU compilation failures with zero physical GPUs, plus tests checking graph construction and configuration. See collectives compilation test and CPU construction tests.

Its purpose remains preparing or checking GPU computations. Actual GPU allocation and kernel execution are unsupported by these virtual devices. See VirtualDevice implementation.

2. What exactly are “slots,” and why highest GPU ID + 1?

Here, “slot” means a position in the zero-based GPU numbering scheme. It is explanatory terminology: the getter stores one integer, not an array of GPU objects.

For a reported count N, the numbering convention is:

Device IDs:  0, 1, 2, …, N−1
Count:       N

Consequently, to accommodate an ID k, the count must satisfy:

k < N

The smallest suitable count is:

N = k + 1

You can see this directly in load_device():

num_devices_available = accelerator_count()

if device_spec.id >= num_devices_available:
    raise ValueError(...)

Example: requesting only GPU ID 3.

count = 3 → advertised IDs are 0, 1, 2
            ID 3 fails: 3 >= 3

count = 4 → advertised IDs are 0, 1, 2, 3
            ID 3 passes: 3 < 4

That is why the helper calculates the highest requested ID plus one. See calculate_virtual_device_count().

Sparse IDs make the distinction important:

Requested GPU IDsNumber requestedRequired virtual count
[0]11
[3]14
[0, 3]24
[2, 7]28

For [0, 3]:

Advertised numbering:  [0] [1] [2] [3]
Requested devices:      ↑           ↑

The count accommodates the original IDs. Loading the requested list creates devices for those IDs; it does not automatically create an object for every intervening position. See load_devices().

Using the list length—2—would fail the existing check for ID 3. Preserving the IDs also lets the parent and compiler workers use the same device specifications.

Why the outer max(1, …)?

The helper starts with highest_gpu_id = -1. If it discovers no GPU IDs:

highest_gpu_id + 1 = −1 + 1 = 0
max(1, 0)         = 1

This gives virtual-device setup a positive count, because 0 disables virtual mode. The CLI calls this helper when enabling virtual mode, before validating device specifications. The floor is a setup convention; it does not establish that a physical GPU exists. See CLI setup and mode predicate.

QnA 3 · In which MAX Serve or MAX example use case do the setter and getter run concurrently?

I did not find a normal MAX Serve or custom-op example where the count setter and getter deliberately run concurrently. My earlier Thread A / Thread B example illustrated a possible data race; it was not a verified MAX execution path.

The actual paths are:

MAX use caseWhat happens
Add-one / fused-attention examplesCall accelerator_count(); they never set the virtual count. See fused_attention.py:29.
CLI target configurationSet the virtual count before validating the requested devices. See config.py:499.
Parallel compiler workersEach worker process sets its own count during initialization, then loads devices and compiles. See compile_pool.py:241.

For the compiler workers:

Worker process 1                    Worker process 2
────────────────                    ────────────────
Initialize: set count = 4           Initialize: set count = 4
             ↓                                   ↓
Compile: read count = 4              Compile: read count = 4

These processes compile concurrently, but each has its own process-local count. Their writes do not race against one shared integer. The globals documentation specifies one copy per process; the pool uses separate processes. See VirtualDeviceGlobals.h:14. (docs.python.org)

So why atomic? It guarantees thread-safe access to this shared configuration if a caller introduces overlapping reads and writes. The source promises that thread-safe API, but it does not identify a specific normal Serve scenario requiring concurrent updates. See VirtualDeviceGlobals.h:47.

The intended lifecycle is configure first → create devices → compile/use them. Compiler workers explicitly require configuration before their first device creation. See compile_pool.py:208.
