Model Manifest roles and Diffusers

Llama 2 7B · single-model manifests · multi-component manifests

A manifest role name is the key that says what a model config is for. ModelManifest is a mapping from role names to MAXModelConfig objects (definition). The role is not the model’s Hugging Face architecture name.

Manifest kindExample entriesMeaning
Single model "main" → MAXModelConfig(...) The primary model being served. For Llama 2, its architecture is read from the Hugging Face config.
Component manifest "text_encoder", "unet", "vae", "scheduler" → individual configs Separate parts of a larger pipeline, each with its own role and often its own checkpoint subfolder.

"main" is a conventional role for a single-model pipeline. Other roles can identify a speculative "draft" model or components such as "vae" and "unet". A component manifest usually has no "main" entry; its non-component details, such as the pipeline class name, are kept separately as manifest metadata. MAX uses these role keys to find the right config for each part.

Hugging Face Diffusers is a library for diffusion models, often used for image or video generation. A text-to-image pipeline typically encodes the prompt, repeatedly denoises an image representation, then decodes it into an image. Those stages use separate components—for example, a text encoder, a denoiser (unet or transformer), a VAE, and a scheduler. A repository’s model_index.json or modular_model_index.json describes its components. MAX checks that index and, when it finds recognized components, builds a config for each component and its subfolder (component discovery). This is conditional: not every repository is treated as a multi-component manifest.

Ordinary Llama checkpoint:
ModelManifest
└─ "main" -> MAXModelConfig(model_path="meta-llama/Llama-2-7b-hf")

Diffusers checkpoint:
ModelManifest
├─ "text_encoder" -> MAXModelConfig(..., subfolder="text_encoder")
├─ "unet"          -> MAXModelConfig(..., subfolder="unet")
├─ "vae"           -> MAXModelConfig(..., subfolder="vae")
└─ "scheduler"     -> MAXModelConfig(..., subfolder="scheduler")

Separate metadata:
_class_name -> "StableDiffusionPipeline"  # illustrative

ModelManifest.from_model_path() first checks for a Diffusers component index. If it finds recognized components, it returns a component manifest. Otherwise, it builds one MAXModelConfig and returns it under "main" (method).

model_path = "meta-llama/Llama-2-7b-hf"
    -> ModelManifest.from_model_path(model_path)
        -> check for model_index.json / modular_model_index.json
            ├─ recognized components found
            │    -> return component manifest
            │    -> caller keeps it
            │
            └─ no recognized components (usual Llama 2 case)
                 -> return {"main": MAXModelConfig}
                 -> caller uses this result as a probe

For Llama 2, "main" is the manifest role for the primary model. The caller keeps a probe only when "main" is absent, so it does not keep this temporary single-model manifest; the flat model_path continues into PipelineArgs (caller). Constructing the config can read Hugging Face config metadata and generation defaults (config population); this step does not load model weight tensors or compile the model.
