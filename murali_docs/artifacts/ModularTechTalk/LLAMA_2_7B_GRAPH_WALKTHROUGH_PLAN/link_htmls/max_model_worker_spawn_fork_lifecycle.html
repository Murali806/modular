MAX model-worker startup

Follow the API parent from lifespan, through a spawned worker, readiness, and HTTP serving.

The example context is max serve --model meta-llama/Llama-2-7b-hf. The timeline starts after MAX has parsed the command and assembled the pipeline configuration, tokenizer, memory plan, and deferred model factory in the API process. It follows repository code; this is not a measured model run.

That earlier API-side configuration can already have populated its process-local _config_cache. The worker is spawned afterward with a separate cache; its access to the Hugging Face disk cache is a different matter.

Readiness has three separate milestones: the worker sets an alive event after reaching its scheduler loop; the API then waits for the ZeroMQ request channel to connect; after the API lifespan yields, Uvicorn enters server.serve() and starts HTTP serving. One milestone does not stand in for the next.

What happens at each step

Expand a step for the source path and why it matters. The API parent is the process that owns FastAPI and Uvicorn; the worker is a separate Python process.

  1. The API serving coroutine enters MAX lifespan

    serve_api_server_and_model_worker() creates the Uvicorn Server object, then its serve() coroutine enters async with lifespan(...). The call to server.serve() is after that context manager. MAX sets Uvicorn's config to lifespan="off" because the entrypoint owns this lifecycle explicitly.

    So at this point a server controller object exists, but MAX has not yet reached the call that starts Uvicorn's HTTP serving. The lifespan first starts telemetry and prepares the API-side serving state.

    serve() and server.serve() order · serve_api_and_model_worker.py lifespan() · api_server.py Uvicorn config sets lifespan="off" · api_server.py

  2. The API lifespan prepares the worker interface and chooses spawn

    Inside lifespan(), MAX constructs a ZmqModelWorkerInterface for request, response, and cancellation queues. It then enters start_model_worker() with the deferred model factory, pipeline config, server settings, metrics factory, interface, IPC endpoint, and memory plan.

    start_model_worker() explicitly selects multiprocessing.get_context("spawn") and creates an Event named alive. This is the concrete process method used for this model-worker path.

    worker interface and start_model_worker() call · api_server.py ZmqModelWorkerInterface · zmq_interface.py start_model_worker() · model_worker.py get_context("spawn") · model_worker.py

  3. The parent schedules a launcher; the launcher starts a fresh child

    There are two different start() calls in this path:

    • ProcessManager.start(...) schedules run_subprocess() as an asyncio task. It returns the task to the API parent.
    • Inside run_subprocess(), MAX constructs _DebugSpawnProcess and calls its proc.start(). This is the multiprocessing call that launches the spawned child interpreter.

    The child target is the callable ModelWorker(), with the event and worker inputs passed as process arguments. In parallel, the parent calls await proc.ready(alive, ...) and waits while child initialization runs.

    Keep the names separate: ProcessManager.start() schedules MAX's subprocess launcher; _DebugSpawnProcess.start() creates the OS process.

    create event and ProcessManager.start() call · model_worker.py ProcessManager.start() schedules run_subprocess() · process_control.py _DebugSpawnProcess construction and process start · process_control.py _DebugSpawnProcess is a SpawnProcess · process_control.py

  4. The new process restores configuration into its own memory

    spawn starts a fresh Python interpreter. The worker's arguments are deserialized there. When a serialized MAXModelConfig is restored, __setstate__() rebuilds Hugging Face repo handles and, when applicable, the Hugging Face and generation config objects.

    _config_cache is a module-level dictionary in each process. The spawned worker has its own newly imported module and cache; it does not receive the API parent's Python dictionary. This does not require a network transfer: Hugging Face Hub files already present in the on-disk cache can be reused by the child.

    MAXModelConfig.__setstate__() · model_config.py rebuild HuggingFaceRepo handles · model_config.py repopulate Hugging Face config · model_config.py per-process _config_cache comment and declaration · _hf_config.py

  5. The child executes the deferred factory and prepares the scheduler

    ModelWorker.__call__() starts a worker event loop and runs ModelWorker.run(). In run(), the child calls model_factory(). This is when the deferred pipeline factory constructs the actual serving pipeline and model.

    For the Llama text-generation path, pipeline construction resolves model weight paths, checks the Hugging Face cache or downloads missing files, and builds/compiles/initializes the graph. Optional configured warm-up follows. Only after that does the worker set up its ZeroMQ queues and load the scheduler.

    Timing distinction: parent-side configuration and tokenizer work can happen before worker creation. Model-weight resolution and model construction happen when the factory runs in the child. A cache hit can avoid a new download, so “weights are resolved here” does not mean every startup transfers them from the Hub.

    ModelWorker.__call__() · model_worker.py ModelWorker.run() · model_worker.py model_factory() execution · model_worker.py weight path resolution call site · text_generation.py download_weight_files() · hf_utils.py worker communication queues · model_worker.py load_scheduler() call site · model_worker.py

  6. The worker signals alive; the API separately waits for ZeroMQ

    After pipeline construction, optional warm-up, communication-queue setup, and scheduler setup, the child enters its scheduler loop. At the top of each loop pass it calls alive.set(). The first set lets the parent's proc.ready(alive, ...) complete; later sets also serve the optional heartbeat watcher.

    This event is a worker-process readiness signal. It is not the ZeroMQ connection handshake and it does not mean Uvicorn is accepting HTTP. After the event, the API creates a ZmqModelWorkerProxy and calls wait_until_connected() to ensure the request PUSH/PULL channel has connected before serving requests.

    worker enters the scheduler loop · model_worker.py alive.set() · model_worker.py ProcessManager.ready() waits for and clears the event · process_control.py parent readiness wait · model_worker.py create API-side worker proxy · model_worker.py wait_until_connected() handshake · zmq_interface.py

  7. MAX completes lifespan startup, then Uvicorn serves HTTP

    After the proxy connects, start_model_worker() yields it to lifespan(). MAX builds the API-side TokenGeneratorPipeline and handler, stores them on app.state, logs its “Server ready” message, and yields from the lifespan context. The entrypoint then resumes and calls await server.serve(...).

    The source order matters: the log is emitted just before lifespan yields; the explicit Uvicorn server.serve() call follows that yield. HTTP requests enter the API process. The API proxy sends request data over ZeroMQ to the worker's scheduler; generated results come back over ZeroMQ and are returned through the HTTP response.

A forked child initially sees the parent's cached values, but it does not share a live mutable Python dictionary. After the fork, parent and child changes are independent.

For this worker: follow the spawn diagram. A fresh worker cache can cause a config object to be reconstructed in the child, while the shared Hugging Face disk cache may avoid fetching the same files again.
