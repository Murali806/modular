What is _config_cache?

Scope · stored value · cache key · process lifetime

Yes: it is a module-level Python dictionary. “Global” here means one dictionary in each Python process that imports the module. The cache stores already-loaded Hugging Face config objects in memory.

Answer · Is it a global variable?

_config_cache is declared at the top level of max.pipelines.lib._hf_config:

_config_cache: dict[HuggingFaceRepo, PretrainedConfig] = {}

That makes it a module-level global dictionary in the current Python process. The key is a HuggingFaceRepo; the value is the loaded Transformers PretrainedConfig (for Llama, normally a LlamaConfig).

One MAX Python process
└── module: max.pipelines.lib._hf_config
    └── _config_cache: dict
        ├── HuggingFaceRepo key ──► PretrainedConfig object
        └── HuggingFaceRepo key ──► PretrainedConfig object

What happens on a cache miss or hit?

load_huggingface_config(repo) checks the dictionary first. On a miss, it loads the config, saves the returned object under that repo key, and returns it. On a hit, it returns the saved object directly.

if repo in _config_cache:
    return _config_cache[repo]       # hit: reuse the object

result = AutoConfig.from_pretrained(repo.repo_id, **kwargs)  # miss: load it
_config_cache[repo] = result
return result

Llama 2 example

repo = HuggingFaceRepo(
    repo_id="meta-llama/Llama-2-7b-hf",
    revision="main",
    trust_remote_code=False,
    subfolder=None,
)

cfg1 = load_huggingface_config(repo)  # loads and caches
cfg2 = load_huggingface_config(repo)  # same key: returns cached object
cfg1 is cfg2                           # True within this process

The key is based on the repo’s identity and settings: repo_id, revision, trust_remote_code, repo_type, and subfolder. A different revision or subfolder therefore gets a separate cache entry. See HuggingFaceRepo.__hash__().

“Global” does not mean shared by every worker

Each Python process has its own module and dictionary. The source notes that a spawned worker starts with an empty cache; a forked worker starts with a copy of the parent’s cache at fork time, then the copies can diverge.

_config_cache = { ... }            spawn  ──► _config_cache = {}
                                   fork   ──► copied cache, then independent

For the call-stack branch: “return this process’s cached config object” means MAX skips another config load in this process and reuses the PretrainedConfig object. The first call may still read a local Hub-cache file or fetch config metadata.
