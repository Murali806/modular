Full answer · where the config is stored and what it contains

PipelineConfig is held by ordinary Python objects in the API process, then passed to the model worker. It is not stored in a global registry. The serve path creates it by calling PipelineConfig.from_args(pipeline_args). It is a resolved configuration object built from PipelineArgs; it is not itself a field inside PipelineArgs.

For a regular single-model Llama 2 checkpoint, PipelineConfig.from_args() first creates a local models dictionary with a "main" entry. It wraps that mapping in ModelManifest and stores it in PipelineConfig.models. The config also carries pipeline-level settings such as sampling, runtime, profiling, task, LoRA, and speculative-decoding settings.

What is .models?

PipelineConfig.models is the configuration object's role map. In the common Llama 2 7B case, pipeline_config.models["main"] returns the MAXModelConfig for meta-llama/Llama-2-7b-hf. It is a mapping keyed by role names, not a global variable or an array. ModelManifest is a dict[str, MAXModelConfig] subclass, so normal mapping access such as ["main"], .get(), and .items() works.

Role keyWhen it appearsWhat the value represents
"main"Usual single-model serving pathThe primary MAXModelConfig; for this example it describes the Llama 2 7B checkpoint.
"draft"When a speculative draft model is configuredA separate MAXModelConfig for that draft model.
Component roleMulti-component modelsA MAXModelConfig for the named component, such as "text_encoder", "unet", or "vae".

The word "main" is a key in this mapping; it is not a Python global called models. During construction, the local dictionary is converted into a ModelManifest and assigned to the models field of the newly constructed PipelineConfig. The manifest maps semantic roles to config objects. It does not contain the model's loaded weight tensors.

Who holds the object in the API process?

After construction, the same API-process config object is passed or referenced in several places. ServingTokenGeneratorSettings.pipeline_config carries it into the server lifespan. The registry's returned factory is a functools.partial with pipeline_config among its bound keyword arguments. During the lifespan, MAX passes the config to start_model_worker(); after worker startup, the API app also assigns that config to app.state.pipeline_config for request handlers to read.

These API-process holders are references to the config object created by PipelineConfig.from_args(); they are not separate model registries. The worker is a different process. MAX selects Python's spawn start method and passes pipeline_config as a process-start argument. The spawned process receives its own deserialized Python object and ModelWorker.run() accepts it as an argument. The worker can then use the config while constructing and running the model pipeline.

Keep these objects separate in your mental model: PipelineConfig is the resolved pipeline-wide settings object; PipelineConfig.models is its role-to-config mapping; each mapping value is a MAXModelConfig; and the worker process receives the configuration as a startup argument. None of these is the Hugging Face weight database or the loaded GPU model.

Example PipelineArgs values · Llama 2 7B

PipelineArgs is the immutable input record assembled from the command-line options (and any config-file values). In the max serve path, Click's parsed keyword arguments are passed to PipelineArgs.from_flat_kwargs(). The option --model is an alias for the internal model_path field.

Command with an explicit task

Command:
max serve --model meta-llama/Llama-2-7b-hf --task text_generation

# Relevant values passed to PipelineArgs.from_flat_kwargs(...):
from max.pipelines import PipelineArgs
from max.pipelines.modeling.types.task import PipelineTask

pipeline_args = PipelineArgs.from_flat_kwargs(
    model_path="meta-llama/Llama-2-7b-hf",
    task=PipelineTask.TEXT_GENERATION,
)

After validation, the task value is represented by the enum PipelineTask.TEXT_GENERATION. The following is a useful view of the fields for this invocation; it is a selected-field example, not the complete printed representation of every nested config.

PipelineArgs (selected values)
├── model_path                  = "meta-llama/Llama-2-7b-hf"
├── task                        = PipelineTask.TEXT_GENERATION
├── huggingface_model_revision  = "main"   # default
├── huggingface_weight_revision = "main"   # default
├── trust_remote_code           = False  # default
├── weight_path                 = []     # discover weights from the repo
├── max_length                  = None   # no --max-length override
├── device_specs                = first visible device # when not specified
└── draft_model                 = None   # no draft model configured

device_specs depends on the machine: if the user does not provide it, MAX selects the first visible device; if none is visible, the default list is empty. Similarly, the nested runtime, sampling, kv_cache, and profiling configs contain their defaults unless a CLI option or config file supplies values. A missing max_length here means “no user override”; later configuration resolution computes an effective model length.

Command without --task

Command:
max serve --model meta-llama/Llama-2-7b-hf

# With no task from CLI or a config file, immediately after parsing:
pipeline_args = PipelineArgs.from_flat_kwargs(
    model_path="meta-llama/Llama-2-7b-hf",
)
pipeline_args.model_path == "meta-llama/Llama-2-7b-hf"
pipeline_args.task       == PipelineTask.UNDEFINED

# The standard serve path identifies the model architecture,
# resolves its task, and makes a new immutable PipelineArgs value:
pipeline_args = pipeline_args.model_copy(
    update={"task": PipelineTask.TEXT_GENERATION}
)

So the first command reaches serving with an explicit task and skips task inference. The second starts with UNDEFINED; MAX infers TEXT_GENERATION for Llama and passes the copied PipelineArgs to PipelineConfig.from_args(). The later PipelineConfig is a separate, resolved object; it is not nested inside PipelineArgs.
