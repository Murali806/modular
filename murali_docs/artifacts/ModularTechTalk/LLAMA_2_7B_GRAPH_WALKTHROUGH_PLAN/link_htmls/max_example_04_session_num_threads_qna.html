Q&A · S1.num_threads

S1.num_threads specifies the requested number of CPU execution threads for MAX’s host runtime. It is optional: leaving it unset lets the runtime choose automatically. See the parameter definition.

For your fused-attention example:

InferenceSession(devices=[device])
└─ num_threads omitted
   ├─ S1.num_threads = None               Python stores the supplied value
   └─ native constructor receives 0      request automatic selection
      └─ NS1.runtimeConfig.numThreads = 0
         └─ CPUDeviceOptions.numThreads = 0

This path is in api.py, InferenceSession.cpp, and EngineContext.cpp.

Why does a GPU example need CPU execution threads? Compiling the graph and preparing the executable model require host work. Your actual compilation follows this path:

Python caller: S1.compile(G1)
└─ compile_async(G1)
   └─ native Engine::Context::compileModel(...)
      └─ AsyncRT::addTask(cpuDevice, compilation closure)
         └─ Q1 schedules the closure on a CPU worker
            └─ compileModelSync(...) performs compilation

Python caller waits in handle.wait()
└─ compilation completes → compile() returns C1

The task submission is in EngineContext.cpp; the Python wait is in api.py. The subsequent session.init(compiled) also schedules model setup on a CPU worker. Source

Why expose a thread count? It controls how much host parallelism the runtime can use. For example, a pool with four workers can execute four independent ready tasks concurrently. A single compilation task does not automatically become four tasks; additional workers help when additional runnable work exists. The pool constructs its workers from the selected count. Source

Two details matter here:

  • None → 0 means automatic selection. The resulting count depends on CPU topology, affinity settings and CPU limits; S1.num_threads remains None rather than becoming the resolved count. Selection logic
  • GPU launch dimensions are configured separately. This attention kernel supplies its own grid_dim and block_dim=32. GPU launch

In this walkthrough, G1 has already initialized the shared MAX runtime. S1 reuses that runtime and Q1 when its options match; it does not necessarily create another pool. Graph initialization · Context reuse
