This page reproduces the explanation and examples linked from the MAXModelConfig._populate_generation_config() branch in the combined startup call stack.

Full explanation · GenerationConfig, model config cache, and examples

How GenerationConfig is populated

MAXModelConfig does not define a nested MAXModelConfig.GenerationConfig class. It stores a Hugging Face GenerationConfig in the private attribute _generation_config and exposes it through the generation_config property.

_populate_generation_config()

At construction time, and again when a config is restored from a worker process, this method checks whether a model path exists. If so, it calls _make_generation_config() and stores the result on that MAXModelConfig instance. It skips placeholder configs with no model path. See MAXModelConfig._populate_generation_config().

_make_generation_config()

This method calls Hugging Face’s GenerationConfig.from_pretrained() using the model repository, revision, trust setting, and optional subfolder. That loads generation settings such as temperature and token limits. If loading fails, MAX logs the failure at debug level and returns a default GenerationConfig. See MAXModelConfig._make_generation_config().

It reads generation settings; it does not construct or load model weights.

How this differs from _config_cache

_config_cache is a module-level, per-process dictionary in _hf_config.py. It caches Hugging Face PretrainedConfig objects—such as LlamaConfig—loaded from config.json. MAXModelConfig._populate_hf_config() assigns the returned object to that instance’s _huggingface_config.

Generation settings follow a separate path: GenerationConfig.from_pretrained() loads them, and MAX stores the result in that instance’s _generation_config.

Examples

Llama 2 7B generation settings

The official meta-llama/Llama-2-7b-hf repository is access-gated, so I could not verify its exact generation_config.json here. The following is the complete JSON from the public NousResearch Llama 2 7B mirror. These values should not be assumed to be the official Meta repository’s values:

{
  "_from_model_config": true,
  "bos_token_id": 1,
  "eos_token_id": 2,
  "pad_token_id": 32000,
  "do_sample": true,
  "temperature": 0.9,
  "top_p": 0.6,
  "transformers_version": "4.31.0.dev0"
}

MAX’s sampling-default adapter keeps only supported sampling fields from the generation config. For this example, the projected values are approximately:

SamplingParamsGenerationConfigDefaults(
    temperature=0.9,
    top_p=0.6,
    top_k=None,
    repetition_penalty=None,
    max_new_tokens=None,
    min_new_tokens=None,
    do_sample=True,
    eos_token_id=2,
)

MAX maps eos_token_id=2 to stop_token_ids=[2] when applying the defaults. The adapter’s supported fields and mapping are defined in SamplingParamsGenerationConfigDefaults and MAXModelConfig.sampling_params_defaults.

The JSON does not set max_length or max_new_tokens. Transformers can fill omitted fields with library defaults, which depend on its version. To inspect the full runtime object for the checkpoint and environment you are using:

import json

print(json.dumps(model_config.generation_config.to_dict(), indent=2, sort_keys=True))

Here, model_config is the relevant MAXModelConfig instance.

Another model with an explicit maximum length

The public TinyLlama 1.1B Chat checkpoint provides this example:

{
  "bos_token_id": 1,
  "eos_token_id": 2,
  "max_length": 2048,
  "pad_token_id": 0,
  "transformers_version": "4.35.0"
}

This checkpoint explicitly sets max_length to 2048. MAX’s sampling_params_defaults adapter does not copy max_length; it supports max_new_tokens instead. The two fields also mean different things in Transformers: max_length limits total sequence length, while max_new_tokens limits newly generated tokens.

For an example with more sampling fields, Qwen2.5-0.5B-Instruct specifies temperature=0.7, top_p=0.8, top_k=20, repetition_penalty=1.1, and two EOS token IDs. Those sampling values are represented by MAX’s adapter; BOS and PAD token IDs are not adapter fields.

Example _config_cache entry and its relationship to MAXModelConfig

_config_cache is keyed by a HuggingFaceRepo object, not by a plain repository-name string. This simplified example shows the kinds of values it can hold:

repo_handle = HuggingFaceRepo(
    repo_id="meta-llama/Llama-2-7b-hf",
    revision="main",
    # Other repo identity and loading settings omitted here.
)

_config_cache = {
    repo_handle: LlamaConfig(
        model_type="llama",
        architectures=["LlamaForCausalLM"],
        hidden_size=4096,
        intermediate_size=11008,
        num_hidden_layers=32,
        num_attention_heads=32,
        num_key_value_heads=32,
        vocab_size=32000,
        max_position_embeddings=4096,
    )
}

The shown LlamaConfig fields are representative architecture metadata from config.json. The cache entry is not a GenerationConfig.

                        ▼
_config_cache[repo_handle] ───────► LlamaConfig
                                         │

                generation_config.json

So one MAXModelConfig can hold both objects: _huggingface_config for model metadata and _generation_config for generation defaults. The process-wide _config_cache is involved in the first path only.

The cache is local to a Python process. A spawned worker starts with its own cache; a forked worker begins with a copy of the parent’s cache and then diverges independently.

Expand _generation_config · checkpoint generation_config.json values

_generation_config is a separate Transformers object. Its checkpoint-supplied values for this same public mirror are:

{
  "_from_model_config": true,
  "bos_token_id": 1,
  "eos_token_id": 2,
  "pad_token_id": 32000,
  "do_sample": true,
  "temperature": 0.9,
  "top_p": 0.6,
  "transformers_version": "4.31.0.dev0"
}

The mirror’s config.json has pad_token_id=0, while its generation_config.json has pad_token_id=32000. They feed two different objects. MAX’s sampling-default adapter does not copy pad_token_id.

Transformers fills other GenerationConfig attributes from the installed library version. Print every runtime value with pprint(model_config.generation_config.to_dict()).

Inspect the actual object at runtime

For a live config, these views expose the public fields, Pydantic private state, and the two Hugging Face objects recursively:

from pprint import pprint

# Public Pydantic fields and computed fields
pprint(model_config.model_dump(mode="python"))

# MAX's private, per-instance state
pprint(model_config.__pydantic_private__)

# Expand the two external Transformers objects
pprint(model_config.huggingface_config.to_dict())
pprint(model_config.generation_config.to_dict())
Lifecycle note: at the initial MAXModelConfig.from_pipeline_args() stage, max_length is None when the user did not specify it. PipelineConfig later asks the architecture to calculate the effective sequence length and stores the result; for Llama 2 the checkpoint metadata includes max_position_embeddings=4096. Similarly, an empty weight_path means MAX has no explicit weight-file override at this point, not that the model has no weights.
