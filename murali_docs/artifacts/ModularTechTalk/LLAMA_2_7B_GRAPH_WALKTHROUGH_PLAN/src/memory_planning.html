Before the worker, MAX makes a memory plan.

Configuration tells MAX what the model needs. Device statistics tell it what is available. MemoryEstimator.plan() combines them into an immutable MemoryPlan that the worker uses later.

QnA 1.1.6.1.3 · How does MAX turn free memory into a KV-cache budget?Read free bytes → apply utilization → subtract static reserves → cap → price the managerSOURCE + EXAMPLE

Follow the budget, one deduction at a time.

EXAMPLE
  1. 1 · Free memoryF = Σ Device.stats["free_memory"]
    24.000 GiB
  2. 2 · Utilization envelopeU = F × device_memory_utilization
    21.600 GiB
  3. 3 · Subtract static estimatesK₀ = int(U − W − A − S)
    9.049 GiB
  4. 4 · Apply allocation capK = min(K₀, allocation cap) − vision reserve
    9.049 GiB
  5. 5 · Price selected KV managerC = kv_cache_memory_size(params, K, batch, length, ...)
    8.063 GiB
  6. 6 · Return planavailable_cache_memory = C; footprint ≈ W + A + S + C
    20.614 GiB

Portable page layout and rounding
Llama 2 7B · one device · two-byte unquantized cache elements

one token: K + V, in every layer
           2 × 32 × 32 × 128 × 2 bytes = 524,288 bytes = 512 KiB

one page:  [ token 0 ... token 127 ] = 128 × 512 KiB = 64 MiB

one 4096-token request:
           [page 0] [page 1] ... [page 31] = 32 pages = 2 GiB

four such requests in a full-context batch:
           4 × 32 request pages + 1 null page = 129 pages = 8.0625 GiB

4097 tokens would require ceil(4097 / 128) = 33 pages in this geometry.
The Llama 2 config in this example bounds max_length at 4096 during construction.

A KV head stores both K and V. Llama 2 7B has 32 KV heads; a grouped-query model with fewer KV heads needs less cache for otherwise equal dimensions. BF16 and FP16 have the same two-byte width, but their supported model-load paths are separate. Choosing a width here changes arithmetic, not MAX's model encoding.

How Jenga differs from the conceptual page drawing
Logical request pagestokens × KV dimensions
→
Cache leavesper-device page bytes + alignment
→
Jenga slabhuge blocks → little pages

Jenga is the default manager at this revision. It tiles per-device leaf pages into a slab, allows alignment padding, and reserves a null huge block. For this single unquantized full-attention leaf, the aggregate page is 64 MiB, so the baseline needs 129 such blocks. Hybrid, quantized and multi-device caches can have different leaf and huge-block geometry.

The registry computes min(budget, max(exact_Jenga_size, generic_size)). Jenga's physical slab uses whole huge blocks, so a saturated budget can include a final fractional remainder that is not allocated.

Actual cache params own the head layout and per-device page geometry; head replication may be allowed for some architectures. The generic estimator divides the budget by data-parallel degree and reports bytes across replicas. Jenga plans one device's share from available_bytes / len(params.devices). This page's arithmetic controls stay with one device and an unquantized cache; quantized scales and alignment are handled by the exact source.

Is the MemoryPlan put inside PipelineConfig?

The estimator returns a separate frozen dataclass. {{ref:factory}} puts it into factory_kwargs, binds those kwargs in a functools.partial, and returns it as RetrievedPipeline.memory_plan too. The factory carries that plan across the spawn boundary. Python object identity is process-local; the child gets a serialized copy of the values, not shared parent memory.

The input PipelineConfig keeps the construction-resolved length/runtime fields. The worker reads the effective batch, device specs, length and cache budget from the plan. Main MAXModelConfig objects can be reconstructed during unpickling; they are configuration objects, not the loaded model.

The baseline uses four 4096-token contexts, page size 128, two-byte unquantized KV elements, one device, no draft/vision reservation and a non-binding allocation cap. It is a calculation, not a captured runtime object.

Limits of footprint and special branches

For the ordinary baseline, footprint = weights + activation reserve + signals + vision reserve + cache budget. In the optional OOM search branch, this revision recalculates total_size as model_weights_size + actual_kv_cache_size, while keeping the earlier committed cache field. The full source is retained so these details remain visible.

Virtual-device cross-compilation bypasses device-memory fitting and returns a synthetic 1 TiB cache budget. A multi-component pipeline without a "main" model takes another path with no language-model KV plan. Those branches are outside the standard Llama exercise. Failure to query device statistics is propagated for KV models.
