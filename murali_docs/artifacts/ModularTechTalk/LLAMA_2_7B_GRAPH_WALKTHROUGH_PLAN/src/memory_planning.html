Before the worker, MAX makes a memory plan.

Configuration tells MAX what the model needs. Device statistics tell it what is available. MemoryEstimator.plan() combines them into an immutable MemoryPlan that the worker uses later.

Checkpoint and encoding assumptions for this example

The official repository's pinned Hub metadata supplies the two safetensors file sizes. Its gated config.json returned HTTP 401 to the unauthenticated request, so the dimensions shown here come from a pinned public NousResearch/Llama-2-7b-hf config. Both revisions and the saved evidence are recorded.

At this MAX revision, {{ref:llama_config_type}} omits float16. Encoding and compatible weight-file discovery run during configuration, before memory planning: {{ref:encoding}}. The official file metadata includes mostly F16 tensors and a small F32 tensor count; an aggregate label alone does not establish a compatible load path.

The documented explicit cast policy covers float32 ↔ bfloat16. This page does not assert that the unchanged FP16 checkpoint successfully serves at this revision. The two-byte, unquantized KV example describes cache geometry under stated assumptions. It is not an inferred generation result or a GPU measurement.

Read all twelve step explanations

1 · Read the main model from PipelineConfig

Inputs: P1 is the existing PipelineConfig. Its models mapping contains a "main" entry referring to M1, the main MAXModelConfig.

  1. The planner reads pipeline_config.model. This property looks up models["main"]; "main" is the component's role.
  2. The property returns the existing config object. The planner stores that reference in its local model_config variable.
  3. If the main entry is missing, the property raises ValueError. Otherwise, the next step can read its accepted context limit and metadata.
P1.models["main"] = M1
P1.model is M1
model_config.max_length = 4096

Result: the planner has the main model's configuration. Model weights and a running model are separate objects created during later stages.

{{ref:planner_model_access|Planner read}} · {{ref:pipeline_main_model|Main-model property}} · P1 fields · M1 fields

2 · Call the selected architecture's initializer

Inputs: the selected architecture declaration has arch.config=Llama3Config. The planner has P1, M1 and the construction-resolved length 4096.

  1. The planner calls the config class selected by the architecture declaration.
  2. It passes P1, explicitly names M1 as model_config, and supplies M1.max_length as the keyword-only max_seq_len.
  3. Because this is a class method, cls is Llama3Config. Its return value will become the planner's arch_config.
Llama3Config.initialize(
    P1, model_config=M1,
    max_seq_len=4096,
)

Result: initialization begins in the API parent so memory pricing can use architecture facts. A1 is created at step 11.

{{ref:memory_init_call|Initializer call site}} · {{ref:llama_arch|Architecture declaration}} · M1 fields

3 · Select the model config and require HF metadata

Inputs: initialize() receives P1 and the explicit M1. M1.huggingface_config refers to the already loaded AutoConfig object H1.

  1. model_config or pipeline_config.model selects the supplied model config. If the argument was omitted, the main-model property supplies it.
  2. The method reads model_config.huggingface_config. This metadata carries dimensions such as hidden width, layer count and attention heads.
  3. If the metadata is None, initialization raises ValueError explaining that a valid HF config is required. Valid metadata is passed to the next helper.
Selected model_config = M1
M1.huggingface_config = H1
H1.hidden_size = 4096
H1.num_hidden_layers = 32

Result: H1 supplies checkpoint facts. This step reads an existing metadata object; its earlier loading path is linked below.

{{ref:initialize_hf_access|Metadata read and guard}} · {{ref:hf_load|Earlier metadata loading}} · H1 fields

4 · Delegate to initialize_from_config()

Inputs: P1, the accepted metadata H1, the selected model config M1, and max_seq_len=4096.

  1. initialize() forwards these values to cls.initialize_from_config().
  2. The pipeline, HF config and model config keep their object references. The accepted length is forwarded as the same keyword argument.
  3. The helper combines checkpoint facts with MAX policies, creates the architecture config, and returns it through the outer method.
cls.initialize_from_config(
    P1, H1, M1,
    max_seq_len=4096,
)

Result: the helper receives all inputs needed for construction. The outer method handles model selection and the metadata guard; the helper performs the field assembly.

{{ref:initialize_delegate|Delegating call}} · {{ref:initialize_config|Configuration helper}} · M1 fields · H1 fields

5 · Read MAX's encoding, cache settings and devices

Inputs: M1 contains the model's MAX policy, while H1 contains checkpoint metadata. M1.kv_cache refers to K1, the KVCacheConfig.

  1. The helper keeps K1 so page size, cache format and prefix-caching settings can be passed into cache parameter construction.
  2. _select_quantization_encoding() selects the model encoding using M1 and the config class's default. This exercise explicitly supplies "bfloat16".
  3. The helper reads M1.device_specs and counts the selected devices. The exercise has one entry, gpu:0.
quantization_encoding = "bfloat16"
kv_cache_config = K1
K1.kv_cache_page_size = 128
device_specs = [gpu:0]
n_devices = 1

Result: checkpoint dimensions will be combined with MAX's chosen encoding, cache policy and placement. These policy values have their own config origins.

{{ref:initialize_settings|Settings read and encoding selection}} · {{ref:kv_defaults|Cache settings}} · M1 fields · K1 fields

6 · Resolve model dtype, cache dtype and DeviceRefs

Inputs: the selected encoding is "bfloat16", K1.kv_cache_format=None, and the device specification is gpu:0.

  1. supported_encoding_dtype() maps the model encoding to DType.bfloat16.
  2. cache_dtype_for_encoding() first checks for an explicit cache-format override. Here it is omitted, so the encoding's cache mapping also selects BF16: two bytes per element.
  3. The helper converts each device specification into a graph placement reference: DeviceRef(spec.device_type, spec.id).
Model dtype = DType.bfloat16
KV dtype    = DType.bfloat16
KV width    = 2 bytes / element
devices     = [DeviceRef("gpu", 0)]

Result: model precision, cache precision and placement are resolved separately. For example, a "float32" cache override would give four-byte KV elements while the model stays BF16. The saved HF torch_dtype="float16" remains metadata; this exercise explicitly chooses BF16 in MAX.

{{ref:kv_dtype|Cache dtype precedence}} · {{ref:initialize_settings|Dtype and device conversion}} · K1 fields

7 · Read dimensions and calculate the attention head width

Inputs: H1 has hidden width 4096, 32 query heads, 32 KV heads and 32 layers.

  1. get_head_dim() uses an explicit HF head_dim field when present.
  2. Otherwise, it calculates hidden_size // num_attention_heads. This checkpoint gives 4096 // 32 = 128 values per attention head.
  3. KV-cache construction uses the KV-head count and layer count alongside this width. Query heads and KV heads are separate fields, even though both happen to be 32 here.
hidden_size = 4096
query_heads = 32
head_dim    = 4096 // 32 = 128
KV heads    = 32
layers      = 32

Result: the cache layout has a width of 128 values per KV head. These logical dimensions become inputs to page-byte calculations later.

{{ref:head_dim|Head-width rule}} · {{ref:kv_construct|Dimension arguments}} · H1 fields

8 · Assemble the KV-cache parameter arguments

Inputs: metadata H1, pipeline P1, the device references, cache config K1, and the resolved BF16 cache dtype.

  1. construct_kv_params() reads the KV-head count, head width and layer count through the architecture's helpers.
  2. It takes the data-parallel degree from the main model config. This example uses 1.
  3. It checks P1.speculative. With speculative decoding disabled, the method supplies speculative_method=None and num_draft_tokens=0.
  4. It forwards these arguments to K1.to_params(). KV-head replication uses this method's default False.
KV heads = 32; head width = 128
layers = 32; devices = [gpu:0]
data_parallel_degree = 1
speculative_method = None
num_draft_tokens = 0
allow_kv_head_replication = False

Result: cache construction receives both architecture dimensions and serving policy. This helper is evaluated while preparing the arguments for A1, before that architecture object is created.

{{ref:kv_construct|KV argument assembly}} · P1 fields · V1 result fields

9 · Apply KVCacheConfig policy in to_params()

Inputs: K1 receives the dimensions and policies assembled in step 8.

  1. to_params() builds shared constructor arguments for the cache parameter object, including dtype, dimensions, devices, parallelism and speculative settings.
  2. Because the call supplies no page-size override, it uses K1.kv_cache_page_size=128. It also propagates prefix-caching and other cache settings.
  3. The is_mla argument keeps its default False, so the function selects MHAKVCacheParams. The alternative MLA branch serves a different attention layout.
page_size = K1.kv_cache_page_size = 128
enable_prefix_caching = True
is_mla = False
selected type = MHAKVCacheParams

Result: MAX's page policy and the model's dimensions are packaged into a concrete cache-parameter subclass.

{{ref:kv_to_params_call|Call arguments}} · {{ref:kv_params|Page policy and subclass selection}} · K1 fields

10 · Return V1: MHAKVCacheParams

Inputs: the constructor arguments from to_params(), with one device, 32 KV heads and 128-token pages.

  1. MHAKVCacheParams applies the common cache-parameter initialization and checks the KV-head layout against the tensor-parallel degree.
  2. With one device and data-parallel degree 1, tensor-parallel degree is 1. All 32 KV heads belong to that device.
  3. The omitted slots_per_page becomes one storage slot per token, so a 128-token page has 128 slots.
  4. The constructed object V1 is returned to the architecture helper. Later memory pricing can use its dtype, layout and page dimensions.
V1: MHAKVCacheParams
dtype = BF16; layers = 32
KV heads/device = 32; head_dim = 128
page_size = 128; slots_per_page = 128
data_parallel_degree = 1

Result: V1 describes the KV layout. In this exercise, each token's K and V across all layers use 2 × 32 × 32 × 128 × 2 = 524,288 bytes, making one page 64 MiB. The worker allocates the physical cache later.

{{ref:kv_params|Returned subclass}} · {{ref:mha_params_type|MHA layout and validation}} · {{ref:value_block|KV byte calculation}} · V1 fields

11 · Create A1: Llama3Config

Inputs: checkpoint dimensions from H1, resolved dtype and device references, max_seq_len=4096, and the constructed V1.

  1. The helper evaluates the arguments for cls(...): dimensions, vocabulary, rotary-position settings, precision, devices and serving policies.
  2. This metadata has rope_scaling=None, so both specialized RoPE-scaling parameter objects remain None.
  3. The default attention multiplier is sqrt(1 / head_dim): about 0.088388 for width 128. An HF attention-multiplier override would take precedence.
  4. The Python config object A1 is created with kv_params=V1 and the accepted length. Its fields become architecture facts for the planner.
A1: Llama3Config
hidden_size = 4096; layers = 32
max_seq_len = 4096; dtype = BF16
kv_params = V1; devices = [gpu:0]
attention_multiplier ≈ 0.088388

Result: A1 owns the resolved architecture configuration, including a reference to V1. Weight-based config finalization and model graph construction occur during the later worker stage.

{{ref:initialize_result|Architecture constructor}} · {{ref:attention_multiplier|Attention scaling rule}} · A1 fields

12 · Return the architecture config to the planner

Inputs: initialize_from_config() has created A1, and A1.kv_params refers to V1.

  1. The helper returns A1. The outer initialize() method returns that same value to MemoryEstimator.plan().
  2. The caller assigns the returned object to arch_config.
  3. The architecture declaration supplies PagedMemoryPlanner, which receives A1. Its estimates use these architecture facts together with the parent's config, weight-size and device-memory inputs.
arch_config is A1
A1.kv_params is V1
planner = PagedMemoryPlanner(A1)
memory pricing → MemoryPlan

Result: architecture initialization is complete. The later planning calculations return the separate MemoryPlan with effective limits and a committed cache budget.

Portable page layout and rounding
Llama 2 7B · one device · two-byte unquantized cache elements

one token: K + V, in every layer
           2 × 32 × 32 × 128 × 2 bytes = 524,288 bytes = 512 KiB

one page:  [ token 0 ... token 127 ] = 128 × 512 KiB = 64 MiB

one 4096-token request:
           [page 0] [page 1] ... [page 31] = 32 pages = 2 GiB

four such requests in a full-context batch:
           4 × 32 request pages + 1 null page = 129 pages = 8.0625 GiB

4097 tokens would require ceil(4097 / 128) = 33 pages in this geometry.
The Llama 2 config in this example bounds max_length at 4096 during construction.

A KV head stores both K and V. Llama 2 7B has 32 KV heads; a grouped-query model with fewer KV heads needs less cache for otherwise equal dimensions. BF16 and FP16 have the same two-byte width, but their supported model-load paths are separate. Choosing a width here changes arithmetic, not MAX's model encoding.

Jenga is the default manager at this revision. It tiles per-device leaf pages into a slab, allows alignment padding, and reserves a null huge block. For this single unquantized full-attention leaf, the aggregate page is 64 MiB, so the baseline needs 129 such blocks. Hybrid, quantized and multi-device caches can have different leaf and huge-block geometry.

The registry computes min(budget, max(exact_Jenga_size, generic_size)). Jenga's physical slab uses whole huge blocks, so a saturated budget can include a final fractional remainder that is not allocated.

Example 2 · Choose the request count, then apply the input-token target
  1. Start from the runtime request count. --max-batch-size 4 sets runtime.max_batch_size=4. The planner uses this candidate. When the flag is omitted, the field initially contains None.

Example 3 · Price four full contexts, then compare the 512-request candidate
  1. Calculate bytes for one token's KV data. Store both K and V across 32 layers, 32 KV heads and 128 values per head. Each value uses two bytes:

    2 × 32 × 32 × 128 × 2 = 524,288 bytes/token = 0.5 MiB/token.

  2. Calculate one page and one full context. A page stores 128 tokens, so it uses 128 × 0.5 MiB = 64 MiB. A 4096-token request needs ceil(4096 / 128) = 32 pages, consuming 32 × 64 MiB = 2 GiB of KV data.
  3. Price four full contexts and the shared null block. Four requests need 4 × 32 = 128 request pages. Add one null block for the pool: (128 + 1) × 64 MiB = 8.0625 GiB.
  4. Compare with the available budget. The shared inputs give int(24 GiB × 0.9 − 12.551319 GiB) ≈ 9.048681 GiB for KV cache. The four-request demand of 8.0625 GiB fits. In the exercise's plain single-leaf geometry, the manager commits that smaller amount: 8,657,043,456 bytes.
  5. Resolve the plan's limits. The 129-block pool leaves 128 usable request pages, enough for four 4096-token contexts. One request could use up to 128 × 128 = 16,384 page slots, but the checkpoint bound is still 4096. The explicit batch candidate is 4, so the resulting fields are planned_max_batch_size=4 and planned_max_length=4096.
Four-request plan, selected fields:

The footprint is the weight estimate plus the committed cache in this zero-activation/zero-signal exercise. It is below the hypothetical 24 GiB free memory, so the optional OOM search is skipped.

Same device budget, but batch size omitted: why 512 can remain in the plan
  1. Start with the GPU fallback of 512. The default input-token target 8192 leaves it unchanged.
  2. Price full-length demand. 512 × 32 = 16,384 request pages consume 1024 GiB. Adding the one null block makes the full demand 1024.0625 GiB.
  3. Use the available byte budget. The demand exceeds 9.048681 GiB. The manager's sizing method returns at most the available budget, so this case commits 9,715,947,126 bytes. The chosen single-leaf geometry fits 144 whole 64 MiB blocks into it: a 9 GiB physical slab, with 143 request pages after the null block.
  4. Check one-request capacity and simultaneous full contexts separately. A single request has a page capacity of 143 × 128 = 18,304 tokens, so the checkpoint's 4096 limit remains. Full 4096-token contexts need 32 pages each, giving floor(143 / 32) = 4 simultaneous full contexts by this page arithmetic.
Result: planned_max_batch_size=512, planned_max_length=4096, with room for four distinct full 4096-token contexts in this pool. The request-count field is a ceiling. Actual admission also needs resident pages; shorter contexts consume fewer pages.

The committed byte budget and the whole-block slab are separate quantities. Here the budget is about 9.048681 GiB, while the physical slab is 9 GiB after block rounding. The scheduler must obey that physical capacity as contexts grow.

Example 4 · Keep batch 4, then reduce the pool to 4 GiB or 1 GiB

Keep the same model, four-request candidate and construction-resolved length of 4096. Change only the exercise's allocation cap, which represents the driver-provided maximum allocation size for a single-buffer pool.

Case A · A 4 GiB pool keeps the single-request length at 4096

  1. Cap the budget. The initial 9.048681 GiB KV budget becomes min(9.048681, 4) = 4 GiB. The manager cannot reserve the full four-context demand of 8.0625 GiB, so it uses the capped amount.
  2. Count usable pages. 4 GiB / 64 MiB = 64 total blocks. Reserve one null block, leaving 64 − 1 = 63 request pages.
  3. Check the longest single request. The 63 pages cover 63 × 128 = 8064 token slots. Since 4096 ≤ 8064, the planned per-request length remains 4096.
  4. Check a set of requests. One full context uses 32 pages and fits. Two full contexts use 64 request pages, exceeding the 63 available. Four shorter contexts can fit when their combined page demand stays within 63.

Case B · A 1 GiB pool lowers the single-request length to 1920

  1. Cap and price the pool. min(9.048681, 1) = 1 GiB, which holds 1 GiB / 64 MiB = 16 blocks.
  2. Remove the null block. The request capacity is 16 − 1 = 15 pages, covering 15 × 128 = 1920 token slots.
  3. Apply the physical-capacity clamp. The construction length 4096 is larger than 1920, so MAX returns planned_max_length=1920. This later clamp applies even if the user explicitly requested 4096. The model config retains its construction-resolved 4096; the worker and scheduler consume the plan's effective length.
  4. Check short batches using whole pages. One 1920-token context fills all 15 request pages. Four 384-token contexts use three pages each, or 12 pages, and fit. Four 480-token contexts each round to four pages, requiring 16 pages, and exceed the pool.
Case B result: planned_max_batch_size=4, planned_max_length=1920, available_cache_memory=1 GiB. A full 1920-token context is a one-request capacity result; dividing 1920 by four would overlook per-request page rounding.

Is the MemoryPlan put inside PipelineConfig?

The estimator returns a separate frozen dataclass. {{ref:factory}} puts it into factory_kwargs, binds those kwargs in a functools.partial, and returns it as RetrievedPipeline.memory_plan too. The factory carries that plan across the spawn boundary. Python object identity is process-local; the child gets a serialized copy of the values, not shared parent memory.

The input PipelineConfig keeps the construction-resolved length/runtime fields. The worker reads the effective batch, device specs, length and cache budget from the plan. Main MAXModelConfig objects can be reconstructed during unpickling; they are configuration objects, not the loaded model.
